The Loop Audit

A reusable rubric for health and fitness apps. It scores whether a product actually changes the user's state — and whether it holds their attention while doing it.

Michael Wong · Principal / Advisor Working framework · September 2026

The core test

Does the product make the user measurably better — and make that improvement legible and worth returning to, at a friction cost the user will keep paying?

01Thesis

Improvement and attention, not one or the other

A retentive loop creates value only when both things are true: the user's state improves — more capability, less pain, better wellbeing — and the loop is engaging and low-friction enough that they keep running it.

Improvement without attention goes unnoticed and unrenewed. Attention without improvement is ineffective.

One correction this forces: dependence on prompts may fall over time, but engagement with the loop should not. A working loop keeps producing new targets and may evolve habits, so the user keeps having a reason to run it. Graduating the user out of the product is not the goal; graduating them out of one objective and into the next one is.

02The loop

The loop, not the layer

Games did not win retention by adding points. They connected a clear objective, appropriately scaled challenge, legible feedback, and a reason to attempt the next cycle. Health and fitness apps often copy the visible layer — streaks, badges, notifications — and leave the loop underneath incomplete.

The Loop Audit tests two things at once: whether the product changes the user's state, and whether it holds attention while doing it. The unit of analysis is not a feature. It is the complete cycle from “what is true?” to “what should I do next?” — and the friction the user pays to run it.

The canonical loop

Seven stages for scoring; four for publishing. Diagnosis maps to Diagnose. Assignment covers Assign and Enable. Verification covers Verify and Coach. Progress covers Progress and Re-enter.

The value compounds only when the output of one stage changes the next. A dashboard that does not alter the prescription is reporting. A plan that ignores performance is content. A streak that rewards opening the app is attendance, not progress.

03Score

Score the loop in eight parts

Rate each dimension from 0 to 5, multiply by its weight, and total to 100. Keep both the weighted score and the raw profile: two products can earn 72 for entirely different reasons.

Minimum evidence standard

Do not infer adaptation from changing content alone. Require a visible or testable connection between user state or performance and the next prescription. Mark every score O, I or X — observed in use, inferred from behavior or documentation, or not testable in the observation window. Only observed scores get published as firm conclusions.

04Friction

Friction is a tax on both axes

Friction suppresses improvement and attention at the same time, and it hides from the eight dimensions because it isn't a job the product does — it's a cost the user pays. Score it separately: for each stage, rate what the user pays to run it — time, equipment, another person, cognitive load, emotional cost — from 0 (negligible) to 3 (blocks the stage for most users).

Measurement friction deserves particular attention. An objective test that needs a second person, or a ten-minute setup, will risk being run rarely — which caps verification and progression however good the instrument is. A product can hold the best measurement in its category and still show the user nothing, because the measurement is too expensive to repeat.

Report the ledger beside the score. Two products with the same weighted total behave very differently when one costs three minutes a day and the other costs an afternoon.

Three cuts that matter more than the headline score

  • The broken-link test. Any core stage below 2 caps the practical loop. A brilliant diagnosis cannot rescue an absent assignment.
  • The causality test. Can the product explain why an input changed a recommendation? Correlation dashboards are not coaching.
  • The graduation test. After 30 days, has the user gained capability, insight or self-efficacy — or only accumulated usage?

Five questions worth carrying into every teardown

  • What does the product know now that it did not know last cycle?
  • What did that knowledge change for the user today?
  • How does it distinguish completion from quality?
  • What compounds after the novelty and the streak anxiety fade?
  • Does the system create capability, or dependence on prompts?

The sharpest closing move

Don't end a teardown with “add more gamification.” End with the missing causal link: use [evidence] to change [assignment], explain [why], and make [progress] visible at [cadence].
